# DART · Formal Software Assurance

**Evidence:** Proposed domain research framework. The equations below are author-defined candidate models, not measured findings or requirements quoted from standards.

**Research focus:** Invariant preservation and refinement between specification and implementation.

## Governing model

```text
G(authorized AND fresh AND valid -> permitted) AND G(NOT authorized -> NOT permitted)
```

G is the temporal always operator. This is an illustrative policy, not a complete security property; prove freshness and authorization predicates separately. Model liveness under explicit fairness assumptions.

**Competing models:** Unit tests alone; syntax-only change gate; unbounded optimistic state machine.

**Required record schema:** State, transition, decision, policy revision, proof assumption, expected outcome, tool version. Extend the schema with provenance digest, units, coverage window, collection permission, missingness reason and transformation revision. Use explicit null values for missing observations; do not turn missing into zero.

## Evaluation contract

Measure Reachable invariant violations, explored states, trace length, proof coverage, runtime overhead. Freeze a mission-specific primary endpoint and acceptable resource cost before tuning. Compare the candidate and baseline on the same scenario/partition. Include a no-intervention or null fixture to detect accidental leakage. Report uncertainty at the independent unit—scenario, channel, device or team—and analyze the worst-performing subgroup rather than relying on a portfolio average.

**Adverse cases:** Concurrent revocation; crash during transition; overflow at schema boundary; reordered benign events.

**Graduate challenges:** State explosion; abstraction unsoundness; undefined behavior; fairness mistaken for a guarantee. For each challenge, distinguish a limitation of the estimator from a limitation of available evidence. Ask whether the parameter is identifiable, whether the mechanism transfers to a new environment and which observation could distinguish rival explanations.

**Resource plan:** TLA+ or an equivalent model checker, bounded reference interpreter, developer and formal-methods reviewer. Before implementation, produce a concrete bill of materials, input size, memory/storage estimate, runtime bound and personnel-hours estimate. No universal cost or readiness claim is made here.

## Applicable data and its limits

[TLA+ specification examples](https://github.com/tlaplus/Examples). Revocation, concurrency, refinement and proof-assumption studies. Document abstraction and fairness; finite model checking is not an unbounded proof; use a separate implementation trace refinement check. Resource budget: TLC/Java or equivalent; state space can dominate RAM. Current status: maintainer repository inspected. Access/rights: Inspect per-project licensing before reuse.
